# geo-story UX 评估报告

评估对象：`geo-story.html`（M1，12 事件 / 第一次传道旅程）
评估日期：2026-10-16
方法：源码审阅 + CDP 实测（1280×800 桌面 / 430×932 移动端）+ 数据层统计
**修复状态：第一轮 11 项全部已解决（§六）；第二轮 3 项交互/相机问题已解决（§七）。**
**第二轮核心发现：验收脚本用 DOM 合成 `.click()` 绕过了命中测试，导致三个真实缺陷长期未被发现（详见 §7.1）。**

## 一、评估依据与标准

### 1.1 评估依据

| 层面 | 具体依据 |
|---|---|
| 产出实物 | `template.html`（约 1180 行）DOM 结构、CSS 体系、全部交互函数 |
| 数据事实 | `data/events.json`（12 事件）、`places.json`（12 地点）、`chapters.json`（6 章）、`routes.json`（4 段）——字段完整性、命名一致性、长度分布均由脚本统计得出，非主观判断 |
| 运行时实测 | CDP 真实时间驱动验收 `verify.mjs`（A–J + A2/A3/A4/D1b/D2/E2/I2），零 JS 错误；关键态截图 f1/f2/f3/f4/f5 目视核对 |
| 视觉呈现 | 桌面端 1080p 截图、移动端 430×932 截图、图例区/时间轴/事件卡/详情页逐项比对 |

### 1.2 评估标准

**A. 信息呈现清晰度**（对应需求一）
1. **内容层级**：用户能否在 3 秒内分辨"这是什么 / 发生了什么 / 接下来是什么"
2. **术语可读性**：非专业读者（教会信徒 / 中文圣经读者）能否无障碍理解，不因术语门槛流失
3. **关键信息突出度**：年代、地点、经文、争议标注是否在正确的视觉层级上
4. **歧义与信息缺失**：是否存在需要用户自己推断的空白，或与最初需求（"地点信息、现在的照片、历史上的艺术作品"）的落差

**B. 展现方式优雅度**（对应需求二）
1. **视觉结构与一致性**：同类信息是否用同构的视觉语言；跨区域（侧栏 / 地图 / 时间轴）是否一致
2. **措辞专业度**：标题、标签、提示语的用词是否准确、克制、专业
3. **阅读负担**：信息密度、每屏信息量、滚动与视线成本
4. **交互友好性**：可发现性、可逆性、状态反馈、无障碍可达性

**严重程度定义**
- **高**：直接损害核心使用目标，用户无法完成主要任务，或与已明确的需求承诺不符
- **中**：明显影响体验或专业观感，用户需付出额外成本才能理解
- **低**：细节瑕疵，不影响任务完成

## 二、总体结论

| 维度 | 评价 |
|---|---|
| 视觉语言一致性 | **良好** —— Apple 极简灰阶体系贯彻完整，图标化改造后类型/地点的形态区分清晰 |
| 内容准确性 | **良好** —— 经文双源交叉校对，学术争议有 note 标注，态度克制 |
| 信息完整度** | **不足** —— 与首轮需求存在明确落差（详见 H-1） |
| 术语门槛 | **偏高** —— 章节名与路线名对目标读者偏生僻（详见 M-1） |
| 首屏引导 | **不足** —— 无任何进入指引，首次使用者需要试探（详见 M-2） |
| 交互可逆性 | **中等** —— 播放结束态、筛选态等缺少明确的"我在哪 / 怎么回去" |

**一句话**：视觉与工程实现已达较高水准（改动的图标化、聚焦视野、数据驱动都有实质提升），但**内容层的"读者友好度"和"需求完整性"是当前主要短板**——视觉做得再优雅，也无法弥补没有照片、没有艺术作品、以及章节名读不懂。

## 三、问题清单（问题 — 影响 — 改进建议）

### 【高】H-1 详情页"图像"区块整体缺失

- **问题**：`data/events.json` 中 12 个事件的 `media` 字段**全部为空数组**（实测统计确认）。详情页 `openEvent()` 中 `renderMedia()` 返回空串，`<div class="d-h">图 像</div>` 整块不渲染。首轮需求明确要求"弹出查看原文（经文）及各种资料（**地点信息、现在的照片、历史上的艺术作品**）"。
- **影响**：详情页当前只有"缘起 / 经文"两层，视觉上留有大片空白，信息密度明显低于预期；"现在的照片、历史上的艺术作品"是本项目区别于普通经文地图的核心差异化价值，完全缺失；12 个事件 0 张图，在"资料丰富"的定位下形成明显落差。
- **改进建议**（按落地成本排序）：
  1. **优先补 4–6 张关键事件的图**（不必全量）：`paphos-sergius`（帕弗石质地基马赛克）、`lystra-stoning`（古代异教祭坛/剧院遗址）、`jerusalem-council`（耶路撒冷模型或公会堂）、`antioch-pisidia-sermon`（彼西底安提阿会堂遗址）。
  2. 数据侧按既有 `media` 模型补：`{ kind: 'photo'|'art', title, src, credit, url }`，`src` 本地 webp（≤300KB），`credit` + `url` 必填（Wikimedia Commons 溯源）。
  3. 界面侧在图像区块补一行降级文案：`图像整理中 · 溯源链接`，避免"整块消失"被误读为"该事件没有资料"。
  4. `renderMedia()` 增加 `kind` 分类小标题（"今日遗存" / "历史艺术"），比混排一格更有信息层次。

### 【高】H-2 首屏无进入指引，用户不知道"可以播放"

- **问题**：进入页面后的初始态是静态地图 + 侧栏列表 + 底部时间轴，**没有任何提示告知"按空格播放故事"或"点击标记看详情"**。这行提示确实存在，但位于时间轴最底部（`.tl-keys`，10.5px 灰字），在 1080p 下几乎不可见。播放按钮在时间轴右侧，字号 12px，无任何视觉强调。
- **影响**：本项目最重要的交互（时间轴故事播放）**默认不可发现**。用户大概率只会去点侧栏列表，退化成普通列表浏览，"随时间轴播放依次弹出事件"的核心设计意图完全落空。这是首屏转化路径上最关键的一环。
- **改进建议**：
  1. 首屏在地图区中央偏上放一次性引导卡：`首次体验？按空格或点 ▶ 播放 12 个事件的旅程故事`，点击任意处即消失（`sessionStorage` 记忆，不重复打扰）。
  2. 播放按钮初始态做视觉升级：加大尺寸 / 加轻微呼吸动画 / 加"播放"文字胶囊，播放后恢复常规样式。
  3. 时间轴底部键盘提示字号从 10.5px 提到 11.5px，颜色从 `--ink-3` 提到 `--ink-2`。

### 【中】M-1 章节名与路线名对目标读者偏生僻

- **问题**：章节名「被召与安提阿教会」「耶路撒冷会议」「教会决议」等属于圣经学术通用语汇，但路线名如 **"Cilician Gates Route"（基利家门户线）、"Pamphylian Route"（旁非利亚线）、"Cilician Gates Route Return"** 直接以英文出现在 `renderStats()`、`journeyLegend`、`toast()` 中。图例里"传道旅程"一栏显示的就是这些英文名。
- **影响**：中文圣经读者/普通信徒遇到纯英文路线名会直接产生理解断层，而图例是**常驻可视元素**（非可选展开），无法回避。侧栏统计区「4 段传道旅程」的数字也缺乏对应的中文语境说明。
- **改进建议**：
  1. `routes.json` 增加 `cn` 字段（中文路线名，如「基利家门户线」），图例与 toast 改为「中文名 · English」双行或「中文名（English）」格式。
  2. 章节名可加副标题：`ch-head` 结构改为 `<b>第一次传道旅程</b><span>AD 46–48 · 塞浦路斯与安纳托利亚南部</span>`，用地理范围帮助读者建立空间直觉。
  3. 侧栏统计「4 段传道旅程」下方补一行微说明：`覆盖 4 条陆路与海路`。

### 【中】M-2 术语"会堂""公会堂""安提阿"在事件详情中无解释

- **问题**：`narrative` 中直接使用"会堂""公会堂""犹太会堂"等宗教史专有场所名词（如 `antioch-pisidia-sermon` 的叙事）。这些词对熟悉圣经的读者不成问题，但对**第一次接触圣经地图的非信徒读者**是理解障碍。
- **影响**：核心叙事文本（详情页最重要的连续阅读段落）的可读性因术语门槛下降。这属于"专业度"与"可读性"的权衡失衡——当前明显偏向前者。
- **改进建议**：
  1. 在 `places.json` 或详情的 `m-row` 中，对关键宗教场所增加一行释义：`地点 · 帕弗 / 今天所在 · 今塞浦路斯帕福斯 / 场所说明 · 会堂：犹太教聚礼与诵经的会堂建筑`。
  2. 采用**首现加注、后续从简**策略：同一术语只在第一次出现时括注，之后直接使用，避免逐句解释造成阅读阻滞。
  3. 该字段同样配置化（`places.json` 加 `gloss`），符合项目"内容只动数据"的架构约定。

### 【中】M-3 事件标题命名规则不一致，与右侧地点标签冗余

- **问题**：实测 12 个事件的标题，命名规则三套并行：
  - **带地点前缀**：`帕弗：士求保罗信主`、`彼西底的安提阿：会堂讲道`、`以哥念：放胆讲道`、`路司得：瘸腿行走`、`路司得：石头之难`、`特庇：旅程最远处`
  - **不带前缀**：`安提阿受差遣`、`归回安提阿`、`写《加拉太书》`、`耶路撒冷会议`
  - **纯描述性**：`回访诸城`

  同时侧栏行末已有独立的地点标签（`.ev-place`），因此"帕弗：""路司得："等前缀与右侧标签**信息重复**（例：`路司得：石头之难` + 标签`路司得`）。
  另有语义不一致：`彼西底的安提阿：会堂讲道` 与 `安提阿：被赶出境` 实为**同一地点**，但后者省略了"彼西底"限定词，在同时存在两个"安提阿"（叙利亚安提阿 / 彼西底安提阿）时构成**歧义源**。
- **影响**：标题冗余消耗横向空间；`安提阿：被赶出境` 的省略会让读者误以为发生在叙利亚安提阿——这是**内容正确性层面的歧义**，不只是风格问题。
- **改进建议**：
  1. **统一规则**：标题去掉地点前缀（地点已由标签承载），只保留事件本身：`士求保罗信主`、`会堂讲道`、`被赶出境`、`放胆讲道`、`瘸腿行走`、`石头之难`、`旅程最远处`、`受差遣`、`归回`、`写《加拉太书》`、`耶路撒冷会议`、`回访诸城`。
  2. 若需保留地点信息以增强地图外的可读性（列表被滚动出视口时），则**全部保留**且用完整限定：`彼西底的安提阿：被赶出境`，绝不做一半省略。
  3. 增加自动一致性校验（可并入 `verify.mjs`）：断言所有 `type` 非 `council`/`letter` 的标题在同一地点下前缀风格一致。

### 【中】M-4 时间轴刻度与实际事件分布不匹配，造成"进度错觉"

- **问题**：时间轴范围 AD 46–67，但**全部 12 个事件集中在 AD 46–49**（前 3.5 年）。刻度均匀分布为 46 / 57 / 67，导致：
  - 所有事件圆点挤在轨道最左侧约 14% 的区间内，重叠严重（AD 46 有 3 个、AD 47 有 5 个），多数圆点被 `.tl-knob`（22px 白圆）遮挡；
  - 用户拖动到 AD 57 会发现"12 个事件全部已亮"，进度条走到 50% 却没有任何新事件发生——**进度与内容脱节**，形成"时间过半，故事结束"的错误感知。
- **影响**：时间轴是本项目的主控件，其刻度与内容密度不匹配会持续误导用户对"故事长度"和"当前进度"的判断。圆点重叠也让"逐个点击时间轴圆点"这条路径基本不可用。
- **改进建议**：
  1. **动态量程**：时间轴上界取 `max(所有事件的最大 from + 余量, D0 + 5)`，当前 M1 应为 AD 46–54 而非 46–67；随章节数据补齐后自动扩展到 67。这样前段密度合理，末段留白表示"后续章节"。
  2. **圆点防重叠**：同一像素区间内的多个圆点按序做**垂直错位**（两行）或水平微偏移，保证每个圆点可点击。
  3. 轨道上补一条**章节色带现状的可视说明**（当前已有 `.tl-band`，但 future 态透明度 0.18 过低，可提到 0.28并加 hover 说明"待补充"）。

### 【中】M-5 详情页打开后缺少"已在地图上"的即时反馈

- **问题**：`openEvent()` 中侧栏立即切换到详情视图，而地图侧的 `mapCore.flyTo()` 耗时 1.0s。点击后约 1 秒内，地图上没有任何可见变化，用户主观上"点了没反应"。此外"在地图上定位"按钮在打开详情时**其实已经自动定位过了**，按钮语义与实际行为不符（点了只是再放大一次）。
- **影响**：点击 → 视觉反馈存在约 1s 空窗，长于一般被认为流畅的 300ms 阈值；按钮语义造成轻微困惑。
- **已核实排除**：本条曾怀疑"播放中点开详情会导致当前事件残留 `.dim` 压暗态"，CDP 实测（播放至 `lystra-lame-walk`、8 个标记处于 dim、点开 `antioch-commission`）结果为 **dimCount 8 → 0，当前标记 `hasDim: false`** —— `openEvent` 先调 `pause()`，而 `pause()` 内的 `applyReveal` 已统一重算 dim，状态一致，**不存在该缺陷**。
- **改进建议**：
  1. 飞行时长从 1.0s 降到 0.7s，点击到视觉反馈控制在 300ms 内。
  2. 「在地图上定位」按钮改为「放大查看」，语义与行为对齐；打开详情时即已定位，无需二次定位。
  3. 长期方向：`openEvent` 手工增删 `.cur` 的写法与 `revealEvent` 的 `applyReveal` 收口逻辑并存，两条路径容易在后续改动中再次分叉，建议统一由 `applyReveal` 统一管理标记状态（当前无 bug，属可维护性建议）。

### 【低】L-1 图例常驻左下角，播放中被事件卡遮挡且信息冗余

- **问题**：`.legend` 固定 `left:16px; bottom:16px`，播放中 `.now`（事件卡）出现在 `bottom:24px; left:50%`。两者在 1280px 宽度下不重叠，但在更窄窗口（1024px 及以下）会相撞。同时图例"传道旅程"栏与统计区"4 段传道旅程"、时间轴的旅程色带三处表达同一组信息。
- **影响**：窄屏下遮挡；同一信息三处呈现，属冗余而非冗余不足。
- **改进建议**：
  1. 图例默认只显示「事件类型」，旅程栏折叠为一行摘要 `4 段旅程 · 点击查看`，点击展开。
  2. 宽度 < 1100px 时图例自动折叠为单个 ⓘ 按钮，点击弹出。

---

### 【低】L-2 统计区"章节已上线 1 / 6"表达方式生硬

- **问题**：统计区第 2 格显示 `1 / 6 章节已上线`，`renderStats()` 中 `online` 的算法是"含有事件的章节数"。这个数字对开发者有意义，对读者是**产品进度**而非内容信息，且"1/6"容易让人误以为项目只完成了六分之一、点进去是空的。
- **影响**：轻度误导 + 产品视角泄漏到读者界面。
- **改进建议**：
  1. 改为内容视角：`覆盖 AD 46–49 · 第一次传道旅程`，或直接把该格替换为「已探索地点 7」。
  2. 若要保留章节信息，放到侧栏底部注脚（现有 `#note` 段落已说明"目前上线第一幕"，位置合适）。

---

### 【低】L-3 移动端地图区域偏矮，事件卡与图例争抢空间

- **问题**：实测 430×932 下 `#map` 高度 522px（约 56% 视口）。图例在 <768px 已 `display:none`（避免了遮挡），但 `.now` 事件卡 `max-width:min(480px, 100%-40px)` 在 430px 宽下几乎占满，`.chips` 四个按钮换行后占两行，加上事件卡的"查看详情"按钮，移动端可用地图面积被明显压缩。
- **影响**：移动端看图与看卡难以兼顾。
- **改进建议**：
  1. 移动端事件卡改为**顶部通栏**（`top:12px; left:12px; right:12px; bottom:auto`），把底部留给地图。
  2. `.chips` 在移动端隐藏"重置视图"文字仅留图标，或收进一个 ⋯ 菜单。

---

### 【低】L-4 英文副标题与中文正文的层级关系可以更清晰

- **问题**：`.sub` 为 `Three Missionary Journeys and the Voyage to Rome`，使用 `--serif` 斜体，与主标题「保罗故事地图」形成双语并置。设计意图是"中文主 / 英文副"，但当前字号 12.5px、灰度 `--ink-2`，与下方正文的区分度主要依赖字体差异，层级偏弱。
- **影响**：轻度。对中文读者是装饰性信息，注意力层级不够明确。
- **改进建议**：
  1. 改为可读性更强的英文正式名：`The Journeys of Paul · AD 46–67`，同时把年代区间显式化，与正文信息呼应。
  2. 或直接删去英文副标题——若不服务任何双语使用场景，删去比保留一个弱层级元素更干净（**需先确认是否面向双语读者**）。

## 四、改进优先级与实施顺序

> **实施结果**：11 项已全部落地（2026-10-16），详见 §六。原计划中"M-1 中英路线名"一项经复核**不存在**（`routes.json` 的 `name` 字段本就是中文），已改为补章节地理副标题。

## 七、二轮修复：交互失效与相机同步（2026-10-16 晚）

用户实测反馈三个问题：**① 无法触发事件详情 ② 点击开始播放没有反应 ③ 缩放与路线播放不同步**。

### 7.1 为什么自动化验收全绿却线上复现

关键发现：现有 `verify.mjs` 的点击断言用的是 **DOM 合成 `.click()`**（`document.getElementById('guide').click()`），
它**绕过浏览器的命中测试（hit testing）**，因此无法暴露「元素在 mousedown 与 mouseup 之间变得不可命中」这一类缺陷。
改用 CDP `Input.dispatchMouseEvent`（真实鼠标事件）后，三个问题全部复现。

**这本身是一条工程教训**：验收脚本的保真度决定了它能发现什么 bug。合成事件断言"看起来在测交互"，
实际只测了"事件监听器绑没绑上"。

### 7.2 P1 / P2 —— 无法触发事件详情、点击播放无反应

| # | 根因 | 修复 |
|---|---|---|
| P1 | `window` 上的 `pointerdown` 监听在**按下瞬间**给引导卡加 `.out`（含 `pointer-events:none`），导致 `mouseup` 落到下层 `#map`，click 的 target 退化为 mousedown/mouseup 的**共同祖先**，引导卡的 click 监听**永不触发** | ① 按下点若在引导卡内则**不**关闭；② 引导卡改为**流内横幅**（`.scroll` 首个子元素）而非 fixed 浮层，占布局高度不覆盖任何元素；③ 只有 `#guideAct` 触发播放，卡片本身不可点 |
| P2 | `body.story-end .ev-dot{pointer-events:none}`（播完隐藏图标）**只进不出**：没有任何地图交互恢复该 class，播完一次后事件详情**永久点不开** | 在地图容器 `pointerdown`（**捕获阶段**）+ `zoomstart` 时 `setStoryEnd(false)`。必须用 pointerdown 而非 click——click 的命中测试发生在 pointerup 之后，等到 click 才恢复的话用户这一下仍然点不中 |

引导卡位置也是问题本身：旧版居中浮层正好盖住地图上事件标记最密集的区域，用户第一次点事件标记只会打到卡片。
改流内横幅后 `A10b` 断言其与 map / playBtn / tlTrack / 事件列表行的交集面积**全为 0**。

### 7.3 P3 —— 缩放与路线不同步（**已重构**）

**原架构是「两个独立动画」**：
- `routes.seek()` 自己跑一个 2.2s 的 rAF 补间画线
- 相机只在事件地点出界时 `flyTo` 一次，缩放硬编码 `6.2`

两者无共享时钟 → 描线在推进时镜头静止不动。

**重构为「同一时钟」**：`route-engine.seek()` 新增 `onFrame(headLatLng, t)` 逐帧回调，
回调里同步执行 `map.setView(ll, z)`——描线每推进一帧，相机就用**同一个插值坐标**重新定位，物理上不可能错拍。
新增 `pointAt(j, dist)` 按里程在路径上取**插值点**（而非直接取 `path[k]`），消除相机逐帧 setView 的顿挫感。

缩放策略：`CAM.zCruise 5.3 → CAM.zEvent 6.4` 按 `t^1.6` 插值——起手拉远看全程，接近事件时推近到特写。

**附带修掉的隐藏缺陷**：M1 的 12 个事件集中在 AD 46–49，相邻事件 `from` 相同 → 年代跨度为 0，
`timeline.animateTo` 走 `Math.abs(span) < 1e-6` 分支直接 `setYear+done`，**过渡耗时 0ms**，
描线与相机补间刚开始就被下一轮重置。这也是"不同步"的第二个成因。
现改为同年事件也保证 `travel` 的过渡窗口，并把 `travel` 提为 `TRAVEL` 常量与描线共用。

`stepEvent`（步进）改走 `routes.seek(ev, 0)` + 显式 `flyTo`，保持无描线动画但镜头仍落到事件地点。

### 7.4 顺带修复：移动端布局塌陷

修引导卡时暴露一个**既有缺陷**：窄屏 `.scroll`（事件列表区）被压到仅 45px，事件列表整体不可见，
且引导横幅会压住播放按钮。根因是 `#map{height:56dvh}` + `.scroll{min-height:0}` 的双重挤压。

修复：地图降至 `37dvh`、压缩 header 留白、章节 chip 改**单行横向滚动**（并钉死 `height:31px`——
`flex:none` 只固定主轴尺寸，交叉轴仍会被容器 `align-items` 拉伸，实测 chip 被拉到 96px 撑高整行）、
窄屏隐藏 chip 计数（计数在时间轴「N / 12 事件」已有）。

实测移动端可视事件行 **0 → 3 行**，`chapterbar` 高度 **110px → 45px**。

### 7.5 新增回归断言

| 断言 | 覆盖什么 | 修复前 | 修复后 |
|---|---|---|---|
| `A10` | **真实鼠标**点击引导卡 CTA 是否开始播放 | `playing: false` | `playing: true` |
| `A10b` | 引导横幅是否遮挡任何可交互元素 | 覆盖地图标记区 | map/playBtn/tlTrack/listRows **全 0** |
| `A11` | 播完后点事件标记能否打开详情 | `detailOpen: false` | `recovered: true, detailOpen: true` |
| `D3` | 相机与描线同步（跨 travel 窗口连续采样 16 次） | 无此断言 | 中心距平均 **2px** / 最大 **7px**；缩放 5.5→6.5 变化；路线点数 1→40 同步生长 |
| `J2` | 窄屏列表区可视行数 | 无此断言 | `visibleRows: 3, ok: true` |

**关于假通过的排查**：首版 `A10b` 写在引导卡**已被关闭之后**才测，此时 `getBoundingClientRect()` 全为 0，
无论实际位置如何都会得出"无重叠"。已移到可见时测量，并加 `if (hidden) return {skipped}` 显式短路。

### 7.6 方法论沉淀

> 交互类断言必须走**真实输入事件**（CDP `Input.dispatchMouseEvent` / Playwright `page.click()`），
> 不能用 DOM 合成事件。合成事件绕过命中测试，而命中测试正是「元素何时可点」这一类缺陷的暴露窗口。
> 断言里凡是要量布局，必须先断言元素**处于可见状态**，否则 `display:none` 后的 rect 全 0 会让任何
> 几何断言无条件通过。

## 八、三轮修复：播放抖动根因与相机 rig（2026-10-17）

用户反馈：**动画播放时抖得厉害，怀疑要换技术实现**。

**结论：不需要换技术。** 问题不在 Leaflet+SVG 选型，而在「跟车相机每帧 `setView`」这个用法上。
Leaflet 自身的 `flyTo`/`setZoom` 就是 transform 通道的平滑动画——把相机运动从「每帧 setView」
改成「rig 只平移 + 离散缩放动画」后，同场景工作量下降 94%，全部回归断言保持通过。

### 8.1 根因（源码级 + 实测双重确认）

`camFollow` 在 seek 每帧回调里执行 `map.setView(ll, z, { animate: false })`。setView 非动画路径走
`_moveStart → _move → _moveEnd` 全事件链，每帧触发 `zoomstart/movestart/zoom/move/zoomend/moveend`：

| 每帧事件 | Leaflet 内部动作 | 代价 |
|---|---|---|
| `moveend` | `L.Renderer._update` → `_updatePaths` | **整个场景**每条 SVG path 重新投影 + 重写 `d`（地中海底图 + 经纬网 + 全部路线 + 圆点） |
| `zoomend` | `L.Renderer._onZoomEnd` | 全部图层再 `_project()` 一遍 |
| `zoom` | `L.Renderer._onZoom` → `_updateTransform` | SVG 容器按**小数缩放**做 CSS transform（Chrome 按新尺度重栅格化） |

叠加第二个问题：`zoomSnap: .5` 下 `_limitZoom` 把按 `t^1.6` 插值的缩放假量化为
**5.5 → 6.0 → 6.5 三次瞬跳**——2.6s 行程里尺度抽搐三次，每次伴随全场景重建。

**实测数据**（headless Chrome，12s 播放窗口，软件光栅 / GPU 合成两种环境一致）：

| 指标 | 修复前（每帧 setView） | 修复后（rig） | 变化 |
|---|---|---|---|
| SVG `d` 重写次数 | 31,466 / 31,101 | 1,868 / 1,870 | **-94%** |
| map `moveend` 次数 | 250 / 247 | 4 / 4 | **-98%** |
| 掉帧（>20ms） | 3 / 5 | 1 / 1 | -67% / -80% |
| 最大帧间隔 | 50.1ms | 33.3ms | -33% |
| 长任务（>50ms） | 1 次 56–58ms | 0 | 消除 |

> 测量工具：`scripts/measure-fps.mjs`（rAF 帧间隔 + `setAttribute('d')` 计数与累计耗时 + 地图事件计数 + longtask 观察器）。

### 8.2 修复方案（不换技术，改用法）

1. **相机 rig 只平移**：`camFollow` 每帧用 `map._rawPanBy(latLngToContainerPoint(head) - 视口中心)` 把镜头移到描线头上。`_rawPanBy` 是纯 pane CSS transform（Leaflet 自己的拖拽/`invalidateSize` 就在用），**零事件、零重投影**。已用 `scripts/experiment-rig.mjs` 验证：一次平移残差 0px，90 帧追赶循环 0 个地图事件。
2. **缩放离散化**：行程起步 `map.setZoom(CAM.zCruise)`（原地拉远，CSS 缩放动画，`_animatingZoom` 期间 Leaflet 主动跳过路径重建）；到达时 `flyTo(ev.ll, CAM.zEvent, .55)` 推近特写。CAM 取值对齐 `zoomSnap`（5.5 / 6.5），落桌不再被二次取整。
3. **rig 与缩放动画不同窗**：描线 seek 延迟 380ms 启动（等缩放动画走完），避免两套坐标系统互相打架；延迟窗口用 `playToken` 令牌防「暂停→重播」竞态。
4. **状态对齐**：rig 只挪 pane，`_lastCenter/_pixelOrigin` 会陈旧。每段行程结束、pause、步进、打开详情前，用一次 `setView(containerPointToLatLng(视口中心), zoom, {animate:false})` 对齐（零位移、一次重建）。
5. 顺带：`timeline.setYear` / `applyReveal` 的每帧 `textContent` 写入加变化守卫，避免无谓 layout。

## 九、播放体验轮：同步 / 慢放 / 过点 / 呼吸 / 地点介绍（2026-10-17）

用户反馈五条：① 路线跟踪要与时间轴同步、到达地点后才弹地点和事件名；② 播放与缩放放慢、要优雅；
③ 路线必须经过地点位置；④ 地点闪烁放慢到呼吸频率；⑤ 地点和事件都支持点击弹介绍窗。

### 9.1 时序重排（①）——同一时钟，到达才弹

旧结构：`playEvents.step → animateTo(年份) → onEvent → revealEvent`，即**年份先走完 travel，路线才开始画**，
两者脱节；且卡片/点亮在行程起点就出现。新结构：

| 时刻（1×） | 动作 |
|---|---|
| 0ms | `onEvent`：`revealEvent` —— 巡航 flyTo 拉远（650ms）+ 延迟 700ms 启动 seek；年份补间同时起步 |
| 700–4200ms | seek 描线 + rig 跟车（同一帧回调）；年份与路线**同一窗口**推进 |
| 4200ms | 到达：seek 末帧与年份终点**双触发** `arriveEvent`（`state.arrivedId` 幂等）——卡片、地点点亮、事件点弹跳、`event:arrive`、推近 flyTo（1.15s） |
| 4200–9400ms | 停留 5.2s（卡片进度条与停留同拍） |
| 9400ms | `onLeave`：收卡、清点亮，进入下一段 |

`.cur`（事件名标签与高亮）加 `arrivedId` 门控：行程途中目标事件既不亮也不压暗（traveling 态），
名称严格在抵达后出现。验收 D4：行程中段采样 `cardShown:false / curDots:0 / fxGlow:0`，
到达后 `card / glow / curDots:1 / zoom 6.5` 全部到位，`cardBeforeArrival:false`。

### 9.2 节奏放慢（②）——全部走可控时长的动画通道

| 参数 | 旧 | 新 | 说明 |
|---|---|---|---|
| TRAVEL 行程总窗口 | 2600ms | **4200ms** | 年份 + 描线 + 跟车同一窗口 |
| 巡航拉远 | setZoom 250ms（CSS 硬编码，无法放慢） | flyTo **650ms** | 见 §9.4 踩坑 1/2 |
| 到达推近 | 550ms | **1150ms** | 与停留重叠：卡片弹出时镜头优雅推近 |
| 详情/步进/定位/筛选飞行 | 700–900ms | 1000–1150ms | |
| 涟漪单程 / 光晕淡入 | 2.9s / 1.4s | 3.6s / 1.8s | 与呼吸同频 |

慢 flyTo 无性能代价：flyTo 每帧 `_move({flyTo:true})` 不触发 Renderer 重投影（实测 14s 播放 d 重写 2081 次、
p95 16.8ms、掉帧 0.2%，与修复前同量级）。

### 9.3 路线精确过点（③）

中点二次贝塞尔 Q(m1, b, m2) 的最近点只到 `b + (a+c-2b)/8`——帕弗→别加→彼西底的安提阿一角实测偏离 0.26°，
路线明显不经过城市圆点。修法：`smoothPath` 在 seg 中点直接写入站点坐标（两侧各一段二次贝塞尔，
站点处形成一个地图尺度下不可见的转角）。D5 回归：四条旅程全部站点 maxDevDeg = **0**（精确）。

### 9.4 地点呼吸（④）

旧 `.place .ring` 单环 4.6s 且 70→100% 强制熄屏，读作「闪烁」。新：**双环错相半周期、5.6s 一叹**
（0→55% 扩张渐隐、55→100% 静息），任一时刻总有一环在呼吸波中，无全局熄屏帧；到达光晕同步进入
5.6s 不透明度呼吸。D6 回归：`rings:2 / name:breathe / duration:5.6s / ring2Delay:2.8s`。

### 9.5 地点介绍窗（⑤）

地点核心点击由「地点筛选」改为「弹出介绍」：名称 / 今天所在 / 场所说明 / 缘起 / 该地事件列表
（行点击跳详情，返回经一层 `placeBack` 栈回介绍窗）/ 放大定位 / 「仅看此地事件」（筛选入口迁移至此，
时间轴与章节筛选不变）。上下文地点（大数/大马士革）仍不可交互。新增 `#p/<id>` 深链。
验收 H：介绍窗开启 → 事件行跳转 → 返回介绍窗 → 筛选 3 行 → 清除 12 行，全通过。

### 9.6 本轮踩坑（详见 plan.md §9）

flyTo 的 duration 是**秒**不是毫秒（误传 1150 → 10 分钟爬行，现象酷似 rig 损坏）；
setZoom 时长硬编码在 Leaflet CSS；rig 与缩放动画必须不同窗；到达双触发要去重；
headless Chrome 默认 prefers-reduced-motion:reduce（动画断言先模拟 no-preference）；
详情窗内 `.ev` 行会留在 DOM（行数断言限定 `#list .ev`）。
